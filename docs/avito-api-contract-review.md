## Собственный аккаунт и User ID

Предоставленный позднее `user_swagger.json` подтверждает:

- `GET /core/v1/accounts/self` возвращает `UserInfoSelf.id` (целое число),
  а также имя, почту, телефоны и ссылку на профиль. В интеграции сохраняется
  только `id` как `AVITO_USER_ID`; остальные поля и токен не логируются.
- Метод принимает заголовок `Authorization: Bearer <access_token>`.
  Для собственного аккаунта поддерживается `ClientCredentials`; для
  стороннего приложения указан `AuthorizationCode` со scope `user:read`.
- `GET /core/v1/accounts/{user_id}/balance/` и
  `POST /core/v1/accounts/operations_history/` также присутствуют, но не
  нужны для определения номера аккаунта и не вызываются установщиком.
- `id` не совпадает по смыслу с `Client ID`, почтой, номером объявления
  или хэшем в `profile_url`. Пример ID из схемы не является ID владельца.
- Автоматическое определение реализовано в
  `scripts/configure_avito_credentials.ps1` после обмена двух API-ключей
  на краткоживущий токен. Успешный `self` не доказывает доступ к прочим API.

Сохранение ключей требует пользовательского скрытого ввода, не сообщений
чата. Локальные тесты используют фиктивные данные; фактическая авторизация
и User ID аккаунта пока не подтверждены.

## Объявления

В предоставленном разделе нет методов создания товарных объявлений,
изменения описания/фотографий, управления остатком или снятия объявления.
Отсутствие этих методов в данном файле не доказывает их отсутствие во всём
каталоге. Для публикации сохраняется XML-контур; полученная отдельно
спецификация автозагрузки подтверждает управление загрузкой по ссылке,
а не создание смартфона JSON-запросом.

| Операция | Контракт | Применение в ISVOI |
| --- | --- | --- |
| Список объявлений | `GET /core/v1/items` | Первичная сверка существующих объявлений и поиск дублей |
| Детали объявления | `GET /core/v1/accounts/{user_id}/items/{item_id}/` | Подтверждение статуса и точной связи через `autoload_item_id` |
| Цена | `POST /core/v1/items/{item_id}/update_price` | Возможное обновление канальной цены после отдельного включения |
| Статистика объявлений | `POST /stats/v1/accounts/{user_id}/items` | Уникальные просмотры, контакты и избранное |
| Аналитика | `POST /stats/v2/accounts/{user_id}/items` | Показатели по объявлениям и периодам, доступность метрик зависит от аккаунта |
| Расходы | `POST /stats/v2/accounts/{user_id}/spendings` | Фактические расходы канала |
| Звонки | `POST /core/v1/accounts/{user_id}/calls/stats/` | Агрегированная статистика звонков |
| Стоимость продвижения | `POST /core/v1/accounts/{userId}/vas/prices` | Получение доступных услуг и цен |
| Покупка продвижения | `PUT /core/v2/items/{itemId}/vas/` | Отдельная платная операция, не входит в первоначальный пилот |

Два дополнительных старых VAS-метода по тексту документации устарели:
`putItemVas` и `putItemVasPackageV2`. Их `deprecated`-флаг не установлен;
ориентироваться только на этот флаг при выборе SDK нельзя.

### Правила сверки

- Список доступен для аккаунта владельца объявлений. Документ предупреждает,
  что авторизованный сотрудник может получить пустой список; это не означает
  отсутствие объявлений компании.
- `GET /core/v1/items` имеет пагинацию `page`, `per_page` и по умолчанию
  выбирает `status=active`. Для полной сверки запрашивать также `removed`,
  `old`, `blocked`, `rejected`, иначе завершённые объявления будут пропущены.
- Для новых объявлений `product_channel_listings.external_id` является XML ID
  `isvoi-<source UUID>`. Уже существующий ID автозагрузки сохраняется после
  точной сверки; нельзя без проверки заменять его новым ID и создавать дубль.
  Числовой Avito ID, URL, наблюдаемый внешний статус
  и время сверки нужно хранить отдельно; эти поля ещё не реализованы.
- `ItemInfoAvito.autoload_item_id` позволяет подтвердить связь с XML ID.
  Значение может быть `null` у объявления без такой связи. Совпадение
  заголовка или цены является только подсказкой для ручной сверки.
- Локальный `listing.status=active` означает включение в фид. Он не
  доказывает прохождение модерации или внешнюю публикацию.
- Товарный статус `sold` не выводится из любого внешнего `removed`/`old`:
  склад остаётся источником факта продажи.
- При XML-синхронизации цена остаётся под управлением Directus. Если позже
  включается API-обновление цены, сначала обновлять тот же источник цены,
  иначе следующая загрузка XML может восстановить прежнее значение.

Указанные в файле лимиты: список — 25 запросов/минуту, детали — 500,
изменение цены — 150. Аналитика v2 и расходы v2 — по одному запросу/минуту.
Статистика v1 принимает до 200 ID; глубина статистики v1/v2 ограничена
270 днями. Недоступная метрика не возвращается и не должна считаться нулём.

## Мессенджер

`info.description` прямо указывает: в категориях «Товары» и «Работа»
Messenger API доступен только при подписке «Максимальный». Для «Услуг»
указаны «Расширенный» и «Максимальный». Следовательно, подтверждённый
владельцем «Расширенный» тариф не подтверждает доступ к чатам наших товаров.
В первоначальном пилоте переписка остаётся в кабинете Avito.

Подтверждённые операции: список/детали чатов v2, сообщения v3, отправка
текста и изображения, загрузка изображения, получение голосового файла,
прочтение чата, удаление своего сообщения, blacklist, просмотр подписок,
отключение webhook и регистрация webhook v3.

Для будущего адаптера:

- `Chat.context.value.id` содержит ID объявления; через отдельную связь
  Avito ID можно найти товар и создать обращение с `source=avito`.
- Чтение истории не помечает чат прочитанным. Команда `read` должна быть
  отдельным действием менеджера, а не побочным эффектом фонового импорта.
- Webhook должен подтвердить приём HTTP 200 за 2 секунды; дальнейшая
  обработка выполняется после сохранения входящего события в очереди.
- Поддерживаются исходящие текст и изображения. Загрузка изображения:
  JPEG, HEIC, GIF, BMP, PNG; до 24 МБ и 75 Мп. WebP в этом списке нет,
  поэтому текущие товарные WebP потребуют подготовки поддерживаемой копии
  именно для отправки в чат. Это не вывод о формате фотографий XML-фида.
- Голосовые сообщения — Opus в MP4, ссылка живёт один час. Типы `file`,
  `video`, `appCall` возвращают пустое содержимое в предоставленной схеме;
  полноценная поддержка этих вложений не подтверждена.
- Текущее общее ядро ISVOI ограничено платформами Telegram/MAX/VK.
  Avito требует отдельного адаптера, миграции допустимых платформ и проверок
  очередей, прав и повторных событий; наличие Messenger OpenAPI этого не заменяет.

## Автозагрузка

Для нового клиента использовать профиль v2 и результаты v4. Старые отчёты
v2/v3 помечены `deprecated`: в описании указано сокращение данных с
2026-09-08 и отключение с 2027-03-08. На дату разбора первое изменение
уже наступило; новый интеграционный код на этих отчётах не строится.

| Операция | Контракт | Применение в ISVOI |
| --- | --- | --- |
| Дерево категорий | `GET /autoload/v1/user-docs/tree` | Найти точный `node_slug`, не подставлять slug сайта |
| Поля категории | `GET /autoload/v1/user-docs/node/{node_slug}/fields` | Типы, зависимости, значения, предупреждения и каталоги |
| Текущие настройки | `GET /autoload/v2/profile` | Снять профиль до любых изменений |
| Изменение настроек | `POST /autoload/v2/profile` | Настроить фид и расписание после отдельного согласования |
| Запуск загрузки | `POST /autoload/v1/upload` | Загрузить файлы из настроенного профиля, не передавать товары в body |
| История загрузок | `GET /autoload/v4/uploads` | Связать запуск с `upload_id` и временем |
| Текущая загрузка | `GET /autoload/v4/uploads/current` | Следить за обработкой |
| Её объявления | `GET /autoload/v4/uploads/current/items` | Ошибки и результаты по `ad_id` |
| Последняя завершённая загрузка | `GET /autoload/v4/uploads/last_successful` | Проверять только после корреляции с нужным запуском |
| Её объявления | `GET /autoload/v4/uploads/last_successful/items` | Проверить все позиции и внешние статусы |
| XML ID по Avito ID | `GET /autoload/v2/items/ad_ids?query=...` | Точное сопоставление существующих объявлений |
| Avito ID по XML ID | `GET /autoload/v2/items/avito_ids?query=...` | Получить внешние ID после загрузки |

### Настройки и ограничения

- Профиль v2 использует `feeds_data`: массив объектов `feed_name`, `feed_url`.
  Старые одиночные `upload_url`/`feed_url` заменены этим полем по описанию
  с 2024-12-23. Запись требует также `schedule`, `autoload_enabled`,
  `report_email`; сохранять неизменяемые настройки из предварительного GET,
  не заменять существующие файлы вслепую.
- Расписание содержит `rate`, `weekdays` (0 = понедельник, 6 = воскресенье)
  и `time_slots` (0..23), время московское. `agreement` означает согласие
  с правилами и обязателен при создании профиля; приложение не принимает
  правила за владельца автоматически.
- `upload` допускается один раз в час и **игнорирует лимиты публикации из
  настроек профиля**. Опубликоваться или активироваться могут все подходящие
  объявления из настроенных файлов. До запуска проверить весь профиль и
  обеспечить отдельный allowlist пилота, а не полагаться на `schedule.rate`.
- Успешный запуск возвращает HTTP 200 без документированного JSON-тела и
  `upload_id`. При таймауте не повторять POST вслепую: сначала сверить историю.
- `current` меняется во время обработки и может вернуть предыдущую загрузку,
  пока новая не обработала ни одного объявления. `last_successful` обновляется
  после обработки всех позиций, но это не гарантия принятия каждого товара:
  возможен `success_warning` с ошибками отдельных объявлений.
- Сохранять `upload_id`, `started_at`, статистику, общие `events`; по позиции
  сохранять `ad_id`, отдельный `avito_id`, `avito_status`, `url`,
  `avito_date_end`, `section` и `messages`. Статусы загрузки и объявления
  нельзя смешивать с `products.stock_status` или локальным listing.status.
- История имеет пагинацию `perPage` до 50, позиции до 100. Обходить все
  страницы; `query` по XML ID принимает разделители `,` или `|`. Отсутствие
  загрузки может дать 404; отсутствие связи ID возвращает nullable-поле,
  а не доказательство продажи или разрешение создать дубль.
- Не выводить публичную доступность из отсутствия `security` у отдельной
  операции: схема задаёт OAuth и/или Authorization на других уровнях,
  а фактические права проверяются read-only запросами аккаунта.

## Авторизация

Спецификации объявляют OAuth `client_credentials` для собственного аккаунта и
`authorization_code` для стороннего приложения. Token URL —
`https://api.avito.ru/token`. Для нашего одного аккаунта базовый кандидат —
`client_credentials`.

`POST /token` принимает `application/x-www-form-urlencoded` с
`grant_type=client_credentials`, `client_id`, `client_secret`. Ответ содержит
`access_token`, `token_type`, `expires_in` в секундах. Время жизни вычислять
по реальному ответу, не фиксировать 86400 из примера. Для этого grant
`refresh_token` не описан: обновление выполняется новым запросом
client_credentials с запасом до истечения и блокировкой параллельных обновлений.

Для сторонних аккаунтов отдельно описаны `authorization_code` с `code` и
`refresh_token` с одноимённым параметром; они не нужны первому пилоту.
В JSON ключи этих двух путей содержат невидимые U+200E после `/token`.
Это аномалия документа: не генерировать клиент с такими URL вслепую,
использовать канонический token URL из OAuth-схемы.

Секреты и bearer token остаются server-only, исключаются из ошибок и логов;
доступ к тарифным методам проверяется отдельно от успеха token-запроса.
