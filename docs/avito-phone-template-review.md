XLSX предназначен для ручной загрузки. Постоянная интеграция ISVOI остаётся
`Directus -> XML по HTTPS -> Avito`, API управляет загрузкой и сверкой.
Этот файл позволяет уточнить значения, но не заменяет полную XML-схему.
Для части полей отсутствуют XML-имена, а скрытые списки плоские: они не
доказывают допустимость комбинации производитель/модель/память/цвет/RAM.
Получить зависимости через category fields API и соответствующие справочники.

## Правила сопоставления

| Поля XLSX | Источник и правило ISVOI |
| --- | --- |
| A / C: Id, AvitoId | Для новых — стабильный `isvoi-<source UUID>`, AvitoId пустой; для существующих сохранить проверенный исторический Id и отдельный AvitoId |
| F: Address | Подтверждённый адрес магазина; альтернатива координатам по комментарию |
| G: Title | Канальный заголовок до 50 символов, без цены/контактов; длинное название сайта не переносить вслепую |
| H: Description | До 7500 символов, фактическое состояние, Passport, комплект и гарантия; не копировать чужие/устаревшие рекламные обещания |
| I / J: фотографии | Для XML прямые HTTPS URL; ImageNames с ZIP нужен только ручной XLSX-загрузке |
| L / N: категория / тип | В книге: `Телефоны` / `Мобильные телефоны`; XML-теги и зависимости подтвердить, не экспортировать `smartphones` или догадку `Смартфоны` |
| O: вид объявления | `Товар приобретен на продажу`, не `Продаю своё` |
| P: Condition | `Новое` или `Б/у`; grade A/B не является значением этого поля |
| R / S / T | Производитель / модель / память: точные значения взаимосвязанного справочника, не предположение по заголовку |
| U: SIM | Только подтверждённый региональный вариант; не копировать SIM + eSIM из примера |
| V / W | Цвет и RAM: значения Avito для конкретной модели; цвет сайта сохраняет коммерческое имя отдельно |
| X: IMEI | Необязателен; полный идентификатор из строки 5 в публичный фид ISVOI не переносить |
| Y: комплект | Подтверждённые коробка и кабель -> `Коробка` и `Провод зарядки`; блок питания не добавлять |
| Z: BoxSealed | Комментарий задаёт условие для новой техники и наличия коробки; не заявлять запечатанность по факту наличия коробки |
| AA: Akb | Для Apple с пробегом фактический процент из текущей диагностики, 0..100 |
| AB: DeviceFlaws | Для б/у: `Включается` / `Не включается`, без вывода об исправности всех функций из одного поля |
| AC / AD | Фактическое состояние экрана/корпуса; grade не заменяет отдельное описание дефектов |
| AE / AF / AG | Название компании / AvitoStatus / почта: не превращать экспортные колонки в XML-теги без отдельного контракта |

## Противоречия и оговорки шаблона

- P5 имеет `Отличное`, хотя dropdown P допускает только `Новое` и `Б/у`.
  Комментарий объясняет: для б/у Avito рассчитывает видимое состояние из
  характеристик и неисправностей. Не переносить отображаемое состояние
  обратно как входное значение Condition.
- Строка 3 помечает обе колонки фото обязательными; комментарии I/J задают
  альтернативу. Для XML нужны `Images/Image`, не два одноимённых XLSX-поля.
- Для Z, AA:AD общая легенда строки 3 не полностью отражает условия в
  комментариях. Окончательное правило сверять с актуальными API dependencies.
- Строка 5 не имеет значения Z, а её `AvitoStatus` — «Истёк срок публикации».
  Это не доказательство текущего остатка, продажи или валидности новой загрузки.
- Id и AvitoId в строке 5 совпадают. Перед переносом существующего объявления
  точно сверить приватный IMEI с inventory, не менять Id и не создавать второе
  объявление по одному совпадению модели/цены. Числовой AvitoId хранить отдельно.
- В примере есть контакты, полный IMEI и рекламный текст. Они не становятся
  подтверждёнными настройками магазина, публичными данными или текущей офертой.

## Фотографии и фактическое состояние

Инструкция и комментарий I2/J2 допускают JPEG/PNG до 25 МБ, максимум 10 фото.
Товарные WebP сайта сохраняются: для Avito подготовить отдельные доступные
JPEG/PNG-варианты или проверить Directus-трансформацию с явным JPEG, размер,
MIME и реальные байты. Одна смена расширения не конвертирует изображение.
Проверять HTTPS-доступ без токена, порядок обложка/галерея и лимит 10.

Цвета Avito включают `золотистый`, `серебристый`, `фиолетовый`, `черный`;
сопоставление с Gold/Silver/Deep Purple/Space Black подтверждать для модели.
Для Grade B с мелкими следами на боковинах нельзя автоматически ставить
«Без дефектов» корпусу. Кандидат «Мелкие царапины» требует редакторского
подтверждения по фактическим следам; исходное пояснение Passport сохраняется.

## Исходное состояние до локальной доработки

Текущий `apps/web/lib/avito-feed.ts` проверяет базовый допуск, наличие цены,
фото и подтверждённого mapping, но не полную схему мобильных телефонов:

1. Зафиксировать XML-поля и условные требования по API/шаблону; добавить
   allowlist полей, запрет IMEI/serial/финансовых данных в произвольных attrs.
2. Валидировать длину заголовка/описания, Condition и справочные комбинации,
   адрес, RAM, комплект, батарею и факты состояния. Нельзя подтверждать mapping
   только по успешно сформированному синтаксическому XML.
3. Подготовить JPEG/PNG, сортировку фото, максимум 10 и проверки доступности.
   Сейчас генератор отдаёт необработанные asset URL, MIME не контролирует.
4. Добавить отдельные поля точной связи AvitoId/URL/наблюдаемого статуса;
   сохранить ID существующих объявлений и провести проверку дублей.
5. Ограничить пилот ровно тремя согласованными товарами, проверить все файлы
   профиля; запуск upload через API не ограничивается лимитом из расписания.
6. После загрузки прочитать результаты v4 по каждой позиции, проверить
   продажу/исключение/DateEnd без предположения, что отсутствие в XML уже
   означает снятие объявления.

Текущий `scripts/test_avito_feed.mjs` использует условные `Condition=Used`,
`Category=Мобильные телефоны`, `GoodsType=Смартфоны`. Это проверка сборки,
экранирования и исключения негодных позиций, не валидный fixture официальной
категории. Перед пилотом нужны отдельные контрактные тесты по новой схеме.

## Локальная доработка 2026-10-04

Предыдущее описание генератора и fixtures выше является историческим.
Добавлены allowlist 1-3 ID, JPEG-трансформации, сортировка/лимит фото,
проверки Condition=Б/у, длин, цен, остатка и приватного складского допуска.
Неизвестные attrs и полные идентификаторы блокируются; ошибки пригодной
позиции закрывают весь пилот. Обновлённые 27 регрессионных тестов проходят.
Кандидаты текущей read-only сверки: `т11`, `т29`, `т37`; это не разрешение
на публикацию и не готовый XML для кабинета.

Полная официальная схема ещё не подтверждена: зависимости модели/памяти/
цвета/RAM, точные XML-теги и реальный JPEG preflight остаются обязательными.
В частности, использование GoodsType требует сверки с XML/API аккаунта.
Set, SIM и числовой AvitoId не сериализуются до отдельной проверки.
Endpoint закрыт `AVITO_PHONE_SCHEMA_VERIFIED=0`; подключение API-ключей
само по себе этот gate не снимает. Проверка существующих объявлений,
отдельные поля AvitoId/URL/статуса, согласование пилота и результат v4
остаются дальнейшими шагами.

Последующий read-only API preflight подтвердил Category/GoodsType/Condition
и 83 поля `mobilnye_telefony`; конкретные каталожные сочетания ещё не доступны
в ответе. Все 18 JPEG-вариантов проверены по HTTP/MIME/байтам/декодированию.
Autoload profile возвращает 403, а т37 имеет unmatched identity; пилот закрыт.
