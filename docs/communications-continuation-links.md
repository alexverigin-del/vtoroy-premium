# Продолжение заявки в мессенджере

После успешного сохранения заявки intake возвращает прежнее поле `telegram_url` и новый массив:

```json
{
  "telegram_url": "https://t.me/isvoi_bot?start=<token>",
  "continuation_links": [
    { "platform": "telegram", "label": "Telegram", "url": "https://t.me/isvoi_bot?start=<token>" },
    { "platform": "max", "label": "MAX", "url": "https://max.ru/isvoi_bot?start=<token>" },
    { "platform": "vk", "label": "VK", "url": "https://vk.me/isvoi?ref=<token>&ref_source=site" }
  ]
}
```

Массив содержит только включённые подключения того же магазина с корректным публичным именем бота. `telegram_url` указывает на тот же объект Telegram из массива и сохраняется для старых клиентов сайта.

На одну заявку создаётся один случайный 32-байтовый ключ в Base64URL. Один и тот же ключ подставляется во все доступные ссылки и хранится в БД только как SHA-256. Первая успешная привязка погашает ключ; остальные ссылки после этого недействительны. Срок действия — 15 минут. Повтор запроса с тем же ключом идемпотентности не выпускает другой ключ.

MAX передаёт параметр `start` в событии `bot_started`; обработчик нормализует его в общую команду привязки. Это соответствует [официальной документации MAX](https://dev.max.ru/docs/chatbots/bots-coding/prepare). VK возвращает `ref` вместе с первым сообщением пользователя; он проходит через тот же сценарий.

Сайт повторно проверяет ответ Directus перед отображением кнопок: только HTTPS, точные хосты `t.me`, `max.ru` и `vk.me`, известная площадка и ключ длиной 43 символа. Подмена хоста, HTTP, неизвестная площадка или неверный формат ключа отбрасываются.

Локальный compatibility-тест создаёт синтетические Telegram/MAX/VK-подключения, проверяет три URL с одним ключом, погашает ключ через старый Telegram endpoint и подтверждает привязку к исходной заявке. Отдельный web-контракт проверяет допустимые ссылки и отклонение подменённых адресов.
