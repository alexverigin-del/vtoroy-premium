# Исходящие вложения MAX и VK

Дата фиксации контракта: 10 сентября 2026.

## Общие правила

- Worker получает только проверенный файл из закрытого хранилища коммуникаций. Общий предел ISVOI — 20 МБ, даже если площадка разрешает больше.
- Подготовка медиа и создание видимого сообщения разделены. Ошибка или разрыв сети до финального `messages` / `messages.send` безопасно возвращает операцию в очередь. После начала финального запроса сетевой результат считается неопределённым и автоматически не повторяется.
- Слот загрузки, загрузка и сохранение медиа не считаются доставкой клиенту. Подтверждением служит только идентификатор финального сообщения.
- URL загрузки принимается только по HTTPS, без пользовательских данных, нестандартного порта и IP-адреса. Для MAX разрешён точный домен ожидаемого типа; для VK — хост самого VK или его `userapi.com` CDN. Токен бота не передаётся на upload-host.
- Все операции остаются последовательными внутри постоянного чата. Ответы менеджера сохраняют приоритет над маркетинговыми заданиями.

## MAX

Официальный цикл состоит из трёх шагов:

1. `POST https://platform-api2.max.ru/uploads?type=...` с токеном в `Authorization`.
2. Multipart-загрузка файла в поле `data` по выданному URL.
3. `POST /messages` с `attachments[].payload.token`.

Маршрутизация:

| Тип ISVOI | `type` MAX | Разрешённый upload-host |
|---|---|---|
| image | `image` | `iu.oneme.ru` |
| voice, audio | `audio` | `omu.okcdn.ru` |
| video | `video` | `omub.okcdn.ru` |
| document | `file` | `fu.oneme.ru` |

Для audio/video токен может прийти вместе со слотом, для image/file — после загрузки. Адаптер принимает оба документированных варианта. Ошибка `attachment.not.ready` переводится в ограниченный повтор с экспоненциальной задержкой. Очередь делает не более восьми попыток подготовки/однозначно отклонённой отправки.

Контракт основан на официальных методах [MAX `POST /uploads`](https://dev.max.ru/docs-api/methods/POST/uploads) и [MAX `POST /messages`](https://dev.max.ru/docs-api/methods/POST/messages).

## VK

Изображения JPEG/PNG/GIF отправляются как нативные фотографии:

1. `photos.getMessagesUploadServer(peer_id)`.
2. Multipart-загрузка в поле `photo`.
3. `photos.saveMessagesPhoto(photo, server, hash)`.
4. `messages.send` с идентификатором `photo<owner_id>_<id>[_<access_key>]`.

Голосовой Opus использует `docs.getMessagesUploadServer(type=audio_message)`. Документы, обычное аудио, WebP и видео используют `type=doc`, поэтому остаются доступны получателю как проверенные файлы. Это сознательный совместимый маршрут для токена сообщества: официальная схема VK 5.199 разрешает `video.save` только пользовательскому токену. После upload выполняется `docs.save`, затем `messages.send` с идентификатором `doc<owner_id>_<id>[_<access_key>]`.

`messages.send.random_id` вычисляется из постоянного ID операции. Повтор однозначно неуспешной отправки использует то же значение и сохраняет защиту VK от дублей.

Контракт сверяется с официальной [схемой методов VK 5.199](https://github.com/VKCOM/vk-api-schema): `photos.getMessagesUploadServer`, `photos.saveMessagesPhoto`, `docs.getMessagesUploadServer`, `docs.save`, `messages.send`. Живой пилот на тестовом сообществе всё ещё обязателен до включения подключения.

## Проверки

`npm run communications:test` покрывает:

- последовательность запросов и тело финальной отправки MAX;
- отсутствие токена бота на upload-host;
- нативное фото VK и устойчивый `random_id`;
- голосовой `audio_message` VK и документный fallback для видео;
- маршрутизацию всех пяти типов ISVOI;
- отклонение подменённых upload-host;
- безопасный повтор подготовки, backoff и повтор той же физической операции;
- классификацию `attachment.not.ready`.
