# S3-резервирование коммуникаций ISVOI

## Назначение

Production-контур сохраняет каждые 30 минут:

- полный PostgreSQL dump в custom format;
- SHA-256-манифест всех файлов Directus;
- SHA-256-манифест приватных вложений коммуникаций;
- детерминированные архивы медиа и самопроверяемый `snapshot.tar`.

Файлы собираются в архивы и находятся в неизменяемых пулах `bundles-v1/directus` и `bundles-v1/private`, где именем объекта служит SHA-256 содержимого. Служебный `directus-health-file` не входит в архив. При неизменном составе файлов архив повторно не загружается. Dump, манифесты соответствия путей и ссылки на media-bundles упакованы в один объект `snapshots/<backup-id>/snapshot.tar`. Такая компоновка не создаёт сотни S3-объектов для одной библиотеки Directus.

Снимок пригоден для восстановления только при одновременном выполнении условий:

1. в `comm_backups` установлены `state = completed` и `external_verified = true`;
2. в S3 присутствует `snapshots/<backup-id>/snapshot.tar`;
3. SHA-256 объекта совпадает со значением `manifest_sha256` в `comm_backups`;
4. внутренний `SHA256SUMS`, media-bundles и `pg_restore --list` проходят проверку.

## Закрытая конфигурация production

Бакет должен быть приватным. Публичная политика, CORS и собственный публичный домен для backup bucket не нужны. Репозиторий содержит только шаблон [`communications-backup.env.example`](../infra/communications/communications-backup.env.example).

На сервере используются два файла с владельцем `root:root` и правами `0600`:

- `/etc/isvoi/communications-backup.env` — пути и имя бакета;
- `/etc/isvoi/rclone.conf` — Access key и Secret key.

Для Beget используется backend `provider = Ceph` с пустыми `region`, `location_constraint` и `acl`. Параметр `no_check_bucket = true` обязателен: Beget разрешает создавать и удалять бакеты только из панели управления. Без этого параметра новый `rclone` перед `PutObject` может вызвать `CreateBucket` и получить `403 AccessDenied`, хотя список существующих объектов читается корректно.

Ключи нельзя передавать в чат, включать в Git, журналы systemd или резервную копию проекта. При их регенерации Beget прежние ключи перестают работать. Новую пару сначала сохраняют во временный файл `root:root 0600`, проверяют запись, обратное чтение по SHA-256 и удаление контрольного объекта, затем атомарно заменяют рабочую конфигурацию и запускают полную копию.

## Установка и расписание

Установка выполняется на Ubuntu от root:

```bash
cd /opt/isvoi
bash scripts/install_communications_backup_on_host.sh
systemctl start isvoi-communications-backup.service
systemctl status isvoi-communications-backup.service --no-pager
systemctl start isvoi-communications-backup-health.service
systemctl list-timers 'isvoi-communications-backup*'
```

Основной timer запускается в `00` и `30` минут каждого часа с допустимой случайной задержкой до 90 секунд. Проверка свежести выполняется каждые 10 минут и переходит в ошибку при возрасте последней подтверждённой копии 45 минут. Целевой предел RPO в 60 минут тем самым контролируется заранее.

Скрипт не удаляет объекты из S3. Локальные staging-каталоги старше 48 часов удаляются только после успешной внешней проверки. Срок хранения и удаление внешних снимков задаются отдельной политикой после измерения фактического прироста и стоимости; до этого история накапливается.

## Проверка восстановления

Репетиция скачивает последний подтверждённый `snapshot.tar`, проверяет SHA-256, получает из S3 два media-bundle и восстанавливает dump в одноразовый PostgreSQL 16 container с ограничением 768 МБ памяти и 0,75 CPU:

```bash
set -a
. /etc/isvoi/communications-backup.env
set +a
/usr/local/sbin/isvoi-communications-restore-rehearsal
```

Контейнер не подключается к сети и удаляется после проверки. Production-БД и production-файлы не изменяются. Успешный результат имеет вид `COMM_RESTORE_REHEARSAL_PASSED` и содержит идентификатор снимка, число таблиц, количество восстановленных файлов и время проверки.

## Аварийное восстановление

Перед восстановлением production нужно остановить все исходящие workers и установить recovery hold. Затем выбрать только снимок со статусом `completed` и подтверждённым SHA-256, восстановить его в отдельной БД, сверить заявки, отказы, очереди и внешние операции. Исходящие отправки остаются выключенными до разбора операций со статусом `uncertain` или `partial`. Перенос восстановленной БД в production выполняется отдельной процедурой изменения состояния и не входит в автоматическую репетицию.

## Ограничение неизменяемости

Скрипт никогда не перезаписывает и не удаляет уже загруженные объекты: `rclone` вызывается с `--immutable`. Администратор аккаунта Beget или владелец ключа бакета технически может удалить данные. Поэтому backup bucket нельзя использовать как рабочее файловое хранилище, а доступ к панели и root-серверу должен быть защищён 2FA и отдельными учётными данными.
