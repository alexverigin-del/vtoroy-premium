# Directus Content Patch Workflow

Production Directus is the source of truth for editor-managed copy. Setup and
seed scripts must not overwrite existing content during a normal deployment.
Use `directus:content-patch` when a reviewed engineering change must update an
existing content record.

## Safety Model

- one patch targets exactly one row through scalar exact-match selectors;
- no more than 20 explicit field or nested JSON paths can change;
- Directus system, lead, import and inventory collections are outside this
  tool's ownership boundary;
- identifiers, timestamps, ownership fields and sensitive fields cannot be
  changed;
- nested changes preserve every unrelated JSON key;
- `--capture-lock` records a SHA-256 snapshot and the available update time;
- preview always runs the generated SQL inside `BEGIN` / `ROLLBACK`;
- apply requires the exact patch ID and a committed, unchanged patch file that
  is already present in `origin/master`;
- apply creates and verifies a fresh database/uploads backup before mutation;
- the SQL `UPDATE` repeats the snapshot hash check atomically;
- Directus restarts after the database write, then site content is revalidated;
- post-apply verification reads the row again and checks every requested path.

The tool writes through PostgreSQL because the public site service token is
read-only. Therefore it does not create a Directus Studio revision attributed
to an editor. The committed patch file, Git commit, verified backup path and
operating-memory entry are the audit trail. Routine editorial work must still
be done in Studio.

## Patch Format

```json
{
  "version": 1,
  "id": "2026-08-22-home-final-closing",
  "description": "Update approved closing copy without touching other fields",
  "collection": "page_sections",
  "selector": {
    "id": "c9f5ef87-cde7-4bf1-a97b-00134a0f5009"
  },
  "changes": {
    "closing_headline": "Approved headline",
    "content.form.submit_label": "Approved button label"
  },
  "remove": ["content.legacy_key"],
  "revalidate": "site-content",
  "lock": {
    "snapshotHash": "generated-by-capture-lock",
    "versionField": "date_updated",
    "versionValue": "generated-by-capture-lock"
  }
}
```

`lock` is generated by the CLI. Do not type or update it manually. If Studio
changes the row after lock capture, preview and apply stop without writing.

## Commands

```bash
npm run directus:content-patch:test

npm run directus:content-patch -- \
  --file directus/content-patches/<patch>.json \
  --capture-lock

npm run directus:content-patch -- \
  --file directus/content-patches/<patch>.json

npm run directus:content-patch -- \
  --file directus/content-patches/<patch>.json \
  --apply \
  --confirm <patch-id>
```

The first two commands are read-only with respect to production. Preview does
execute the proposed `UPDATE`, but only inside a transaction that is always
rolled back.

## Operator Rules

1. Inspect Directus Activity before preparing a patch if an editor may be
   working on the record.
2. Keep every patch small enough to explain in one sentence.
3. Commit and push the reviewed patch before production apply.
4. Never combine schema/permission work and copy changes in one patch.
5. Treat a snapshot mismatch as a required re-review of the new Studio state.
6. Record the patch ID, backup path, audits and deploy commit in
   `docs/project-operating-decisions.md` after a production apply.
