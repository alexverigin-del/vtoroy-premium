# ISVOI: товарный контур, маржинальность и Avito

Этот контур принимает полную выгрузку текущих остатков и отдельный файл
поступления. Он хранит закупку, полный serial/IMEI и unit-экономику только в
приватных коллекциях Directus. Публичный каталог обновляется исключительно
после ручного допуска позиции.

## Роли источников

- Полная выгрузка — источник текущего остатка и розничной цены.
- Поступление — исторический источник закупки, даты, серийных номеров,
  комментария о движении и плановой экономики. Оно не меняет остаток.
- Основной ключ — `source_system + Uuid`; код и штрихкод используются для
  проверки. Fuzzy-match допустим только как подсказка для несерийного товара.
- Серийная позиция считается совпавшей только при одинаковом serial и
  нормализованной идентичности товара. Расхождение создаёт blocker.

Исходные рабочие книги содержат коммерческие и идентификационные данные и не
коммитятся в git.

## Работа в Directus Studio

Рабочая навигация разделена по ответственности:

- `Склад и сверка` — snapshot, проблемы активной партии, остатки и поступления;
- `Карточки сайта` — фото, описание, Passport, QA и публикация;
- `Avito и экономика` — category mapping, объявления, расходы и unit-экономика.

Не нужно создавать товар вручную сразу в `Карточках сайта`. Сначала он должен
пройти складскую сверку и получить допуск. После apply связанная карточка
появляется в пресете `Нужны фото`, а складская строка — в пресете
`4 · Передано в карточки сайта`.

Оператор с ролью `ISVOI Inventory Manager` открывает `Товарные snapshot`
(`inventory_import_batches`):

1. Создаёт партию со стабильным именем и датой snapshot.
2. Загружает полную XLSX-выгрузку и при наличии XLSX поступления в папку
   `ISVOI Inventory Imports`.
3. Запускает Flow `ISVOI: проверить товарный snapshot`.
4. Проверяет счётчики и связанные `Проблемы сверки`. Полные serial/IMEI и
   себестоимость не переносятся в публичные коллекции.
5. Запускает apply только после разбора blocker-строк. Повторный apply
   идемпотентен.

После успешного apply предыдущие завершённые партии получают статус `Архив`,
а их нерешённые issue закрываются как исторические. Записи и протоколы не
удаляются, но рабочие пресеты показывают проблемы только активной партии.

### Разбор и закрытие проблем

Поля причины (`Критичность`, `Партия`, связанная складская позиция, код и
описание) создаются проверкой и доступны только для чтения. Оператор открывает
связанную складскую позицию, принимает отдельное решение по происхождению и
допуску, затем заполняет `Как решено` и включает `Решено`.

- закрытие без `Как решено` отклоняется сервером;
- закрытая проблема остаётся в представлении `4 · Решённые проблемы`;
- само закрытие не меняет `authenticity_status`, `eligibility_status` и связь с
  карточкой сайта;
- повторный apply той же партии сохраняет документированные решения по ключу
  `source_kind + code + source_id + row_number`;
- закрытые исторические проблемы, которых больше нет в результате проверки,
  не удаляются.

Строки поступления автоматически получают структурированный статус движения:

- `in_store` — позиция связана с положительным текущим остатком магазина;
- `partial_central_office` — часть количества есть в магазине, разница явно
  помечена как ЦО;
- `central_office` — позиция отсутствует в магазине и явно оставлена в ЦО;
- `central_office_inventory_conflict` — комментарий говорит ЦО, но весь объём
  одновременно присутствует в snapshot магазина; такая строка требует сверки;
- `exited_preload` — позиция отсутствует в текущем snapshot и считается
  проданной, обмененной или иначе выбывшей до загрузки.

Для этого в Studio есть представления `Сейчас в магазине`, `Центральный офис`,
`Выбыло до загрузки` и `Требует сверки места`. Неявно определённое выбытие
создаёт warning, но не blocker: историческая строка не должна блокировать
актуальный склад. `Дата поступления` сохраняется; столбец IMEI необязателен.

Если ранее известная позиция исчезла из полной выгрузки, dry-run показывает
`missing_from_snapshot`, но не меняет данные. Обнуление разрешается только
после включения `Разрешить обнуление отсутствующих позиций`; при этом товар
получает нулевой остаток, а активное канальное объявление возвращается в draft.

## Допуск в Catalog V3

Новая строка остаётся только в `inventory_items` со статусом `pending` или
`blocked`. Для создания/обновления черновика `products` Inventory Manager
должен одновременно:

- установить `authenticity_status = verified` или `not_required`;
- установить `review_override = true`;
- заполнить `review_note` фактическим основанием проверки;
- установить `eligibility_status = eligible`.

Созданный товар всегда получает `status = draft` и
`content_status = needs_photo`. Публикация требует обычного QA Catalog V3:
категории и бренда, положительного остатка, карточного/основного изображения,
гарантии; для техники с пробегом — Passport, grade, батареи и даты диагностики.

При следующих snapshot складской контур обновляет у связанной карточки только
свои поля: SKU, цену, количество, статус остатка и служебную ссылку на партию.
Название, модель, категория, редакторский статус, статус публикации и статус
объявления Avito не сбрасываются. Если позиция исчезла из полной выгрузки,
обнуление и возврат активного объявления в черновик требуют отдельного
подтверждения оператора.

Replica, Mini iPhone-подобные устройства и товары с неподтверждённым
происхождением никогда не допускаются автоматически. Ручной допуск возможен
только после проверки Inventory Manager и при однозначном публичном обозначении
реплики в карточке и канальном объявлении; до появления такого подтверждённого
контента позиция остаётся `blocked`. Identity-конфликт сначала исправляется в
источнике. Значение `ассорт.` требует разделения вариантов либо режима продажи
по запросу.

Дополнительные правила нормализации актуальной выгрузки Evotor:

- электробритвы и триммеры относятся к `smart-electronics`, даже если в
  исходнике временно указана только корневая группа «Товары на продажу»;
- низкая закупочная цена JBL Flip создаёт `authenticity_review`; товар не
  допускается в Catalog V3 и Avito до документированной проверки происхождения;
- UUID остаётся основным идентификатором, а код и штрихкод проверяются как
  внутренние контрольные ключи и не заменяют UUID при повторном snapshot.

## Unit-экономика

`channel_cost_profiles` хранит подтверждённые ставки комиссии, эквайринга,
налога, возвратного резерва, продвижения, доставки и прочих переменных затрат.
Read-only представление `product_unit_economics` рассчитывает gross profit,
gross margin, variable cost, contribution и contribution margin.

Начальные профили `site` и `avito` имеют нулевые ставки и
`is_confirmed = false`. Такие расчёты считаются неполными и не используются для
ценового решения, пока Inventory Manager не подтвердит ставки.

## Avito

### Подключение тарифа и следующий пилот (2026-10-04)

Владелец подтвердил подключение расширенного тарифа Avito на месяц.
Дата активации, дата окончания и доступные аккаунту API-методы пока не
проверены в кабинете; наличие тарифа само по себе не считается успешным
запуском автозагрузки.

Актуальный адрес официального каталога:
[Avito API](https://www.avito.ru/developers/api-catalog).
Для запуска сохраняется связка `Directus -> XML feed -> Avito`; API добавляется
для разрешённых аккаунту операций и сверки результатов загрузки. Отдельный
способ создания товарных объявлений через JSON пока не подтверждён.

Порядок запуска:

1. Проверить доступ к автозагрузке в кабинете. Получены пять API-разделов и
   XLSX мобильных телефонов с одним существующим объявлением и справочниками.
   Сверить обязательные XML-поля и зависимости через category fields API
   либо официальный XML-шаблон; XLSX-справочники не доказывают совместимость
   произвольной комбинации модели, памяти, цвета и RAM.
2. Контракты и ограничения зафиксированы в `avito-api-contract-review.md`:
   для своего аккаунта `client_credentials`, профиль v2, результаты v4.
   Не использовать deprecated отчёты v2/v3. Для read-only сверки сохранить
   `AVITO_CLIENT_ID`, `AVITO_CLIENT_SECRET` и `AVITO_USER_ID` в защищённой
   серверной конфигурации; значения не помещать в чат, git или журналы.
3. Повторно сверить склад и выбрать три доступных опубликованных смартфона.
   Кандидаты `т10`, `т11`, `т12` из сверки 2026-09-17 требуют новой проверки
   остатка перед публикацией.
4. Проверить уже размещённые объявления, включая истёкшие, и их точную связь
   с товарами. Сохранить исторические Id; AvitoId хранить отдельно. Затем
   заполнить category mapping, атрибуты, расходы и тексты по схеме. Шаблон
   содержит полный IMEI: это приватный ключ сверки, не поле публичного фида.
5. Доработать контрактную валидацию и JPEG/PNG-варианты фото, проверить XML,
   включить только три согласованных объявления. Проверить весь профиль:
   `POST /autoload/v1/upload` обходит лимит публикации из его настроек и
   может активировать все подходящие объявления из всех настроенных файлов.
   Проверить результаты v4 по каждой позиции и связь с конкретным upload_id.
   Расширять выборку после 72 часов успешной работы пилота.
6. Подтвердить поведение при продаже, брони, изменении цены и завершении
   подписки: исключение товара из локального XML не является доказательством
   снятия объявления на площадке; результат подтверждается отчётом Avito.

### Данные и правила экспорта

Разбор всех пяти полученных API-разделов:
[`avito-api-contract-review.md`](avito-api-contract-review.md).
Разбор XLSX, обязательных полей и отличий текущего генератора:
[`avito-phone-template-review.md`](avito-phone-template-review.md).
Раздел «Объявления» подтверждает чтение статусов, статистику и изменение

### Хранение API-ключей

Рекомендуемый файл: `/home/deploy/.config/isvoi/avito.env`, вне `/opt/isvoi`
и Git. Владелец `deploy`, каталог `700`, файл `600`. Поля:
`AVITO_CLIENT_ID`, `AVITO_CLIENT_SECRET`, `AVITO_USER_ID`. Они нужны API-клиенту,
но не браузеру и не генератору XML; отдельный файл не подключается в Next
автоматически. Будущий CLI может использовать Node `--env-file` с этим путём,
не передавая значения в аргументах команды.

Для первоначального ввода предусмотрен
`scripts/configure_avito_credentials.ps1`: маскированный `Read-Host`, передача
через SSH stdin, запись с проверкой прав, без локального credential-файла.
Перед запросом ключей выполняется SSH preflight с фиксированным тестовым
JSON. Код передаётся Base64-аргументом `sys.argv[1]`, без вложенных двойных
кавычек: Windows PowerShell 5.1 иначе удалял кавычки и вызывал SyntaxError
до авторизации и записи. Проверка реального транспорта без ключей:
`powershell.exe -NoProfile -File scripts/test_avito_credentials_transport.ps1`.
Вводятся только `AVITO_CLIENT_ID` и `AVITO_CLIENT_SECRET`, не почта и не
пароль Avito. На сервере выполняются `POST /token` с `client_credentials`
и `GET /core/v1/accounts/self`; поле `id` автоматически сохраняется как
`AVITO_USER_ID`. Контракт подтверждён предоставленным `user_swagger.json`.
Хэш из URL профиля и номер объявления не являются этим числовым ID.
Редиректы и прокси из окружения запрещены, TLS проверяется стандартной
библиотекой; таймаут 20 секунд на запрос, без автоматических повторов.
При ошибке авторизации/чтения аккаунта новый credential-файл не создаётся.
Токен существует только в памяти, персональные поля ответа не сохраняются
и не выводятся. Скрипт показывает только подтверждённый ID и результат
проверки файла. Тесты: `python scripts/test_avito_credentials.py`.
Существующий серверный файл и symlink-пути отклоняются; ротация является
отдельным действием. Ввод выполняется в пользовательском PowerShell, не
через обычные сообщения или универсальную форму вопросов чата. Ключи всё
равно кратковременно находятся в памяти процесса; это не секретное хранилище
и не основание отправлять их в чат.

Успешное сохранение файла не включает фид, не меняет настройки Avito и не
подтверждает доступ к автозагрузке, объявлениям или Messenger: проверяется
только авторизация и чтение собственного аккаунта. Credential-файл требует
отдельной шифрованной политики backup, не включается в обычный архив проекта.
Значения не передаются третьим лицам и не логируются; при утечке секрет
ротируется в кабинете.

### Локальное усиление генератора (2026-10-04)

Фактическая read-only сверка после сохранения ключей:
[`avito-account-preflight-2026-10-04.md`](avito-account-preflight-2026-10-04.md).
Авторизация/self/items работают; профиль Autoload возвращает 403, причина
уточняется в кабинете/поддержке. API подтвердил Category/GoodsType/Condition,
но не каталожные комбинации. Проверены все 18 JPEG фото кандидатов.
У т37 identity=unmatched, строгий складской guard его блокирует. Эти результаты
уточняют первоначальную подготовку ниже; draft/mapping и флаги не включались.
Владелец подтвердил, что кабинет принимает файл и URL. Первый пилот после QA
подключается оператором по ссылке в кабинете; устранение 403 API не является
зависимостью этого пути. До включения проверить все существующие URL и
расписание через UI. API profile/upload не используются до подтверждения прав.

Новый генератор проверяет длины, цену и остаток, допустимые значения состояния,
батарею Apple, основные поля модели, соответствие категории и приватный
складской допуск. Неизвестные/приватные attrs блокируют весь пилот, а не
сериализуются произвольными XML-тегами. Полные идентификаторы склада читаются
только server-side для проверки утечки через текст; в ответе и диагностике
возвращаются XML без идентификаторов либо безопасные коды ошибок.

Обязателен `AVITO_FEED_ALLOWED_IDS`: 1-3 точных внешних ID, без дублей.
Флаг `AVITO_PHONE_SCHEMA_VERIFIED=0` сохраняет endpoint закрытым, пока не
подтверждены XML-теги и зависимости модели по официальной схеме аккаунта.
Проверка формата памяти не заменяет проверку комбинации Model/MemorySize/Color/RamSize.
В частности, GoodsType сохраняет существующий mapping-контракт; его точное
применение к мобильным телефонам ещё требует официальной XML-сверки.
Set, зависимый BoxSealed, SIM и AvitoId не сериализуются до отдельной проверки контрактов;
комплект остаётся в обычном текстовом описании. Точный AvitoId пока не
сохраняется в схеме: миграция и сверка существующих объявлений остаются впереди.

JPEG URL использует `format=jpg`, `fit=inside`, 1600x1600, quality=90.
Обложка первая, галерея сортируется, дубли удаляются, максимум 10 фото.
Реальные MIME/размер/декодирование и права asset-трансформаций нужно проверить
до пилота. Код не изменяет WebP сайта и не загружает дополнительные файлы в CMS.

Read-only сверка production выбрала кандидатов `т11`, `т29`, `т37`, все
с остатком 1 и draft-объявлением. Подготовка сохранена локально в игнорируемой
`outputs/avito-pilot-2026-10-04/pilot-preparation.json`; это не готовый файл
загрузки. Цвет, RAM, состояние и адрес требуют подтверждения. Остатки
перепроверяются непосредственно перед запуском. У `т30` модель, цена и
батарея похожи на строку XLSX с истёкшим объявлением, но это только подсказка,
не доказательство идентичности и не разрешение создать второй ID.

`channel_category_mappings` отделяет внутренние категории сайта от значений
официального шаблона Avito. Для каждой активной `product_categories` создаётся
начальная строка канала `avito`; внутренний slug (`smartphones`, `watches`,
`smart-electronics` и другие) никогда не экспортируется как категория Avito.
Категория сайта может иметь несколько mapping с разными стабильными
`mapping_key`: это нужно для широких разделов вроде `smart-electronics`, где
смарт-очки, камеры и фотопринтеры могут относиться к разным веткам Avito.

После текущей сверки товарной структуры:

- часы и браслеты используют внутреннюю категорию `watches`;
- смарт-очки входят в `smart-electronics`, отдельная публичная категория для
  одной позиции не создаётся;
- кабели из складской группы «Зарядные устройства» относятся к `chargers`;
- пустые активные категории остаются в Directus, но не появляются на сайте и
  не могут попасть в Avito без товара и подтверждённого mapping.

Inventory Manager заполняет в mapping точные `Category`, при необходимости
`GoodsType` и код категории, общие атрибуты, а также дату/версию скачанного
официального шаблона. `is_confirmed` включается только после проверки XML.
Предзаполненных догадок о значениях Avito нет: начальные строки создаются
неподтверждёнными.

`product_channel_listings` хранит стабильный `external_id` вида
`isvoi-<Uuid>` для новых объявлений; для уже существующих сохраняется точный
исторический Id после сверки. Числовой AvitoId хранится отдельно и требует
доработки схемы. Коллекция также хранит ссылку на category mapping, ручную канальную цену и атрибуты
выбранного шаблона. Старое поле `category_code` сохранено только для обратной
совместимости и feed его не использует. Endpoint
`/integrations/avito/feed.xml`:

- закрыт флагом `AVITO_FEED_ENABLED=0` до завершения пилота;
- отдаёт только активные объявления опубликованных и готовых товаров с
  положительным остатком и опубликованным изображением;
- возвращает `X-Robots-Tag: noindex, nofollow` и `Cache-Control: private,
no-store`;
- не включает закупку, маржу, полный serial/IMEI и внутренние заметки.
- исключает объявления без активного подтверждённого category mapping;
- объединяет общие атрибуты mapping с атрибутами конкретного объявления.

До включения зафиксировать актуальную XML-схему нужной категории по
category fields API или официальному XML-шаблону и проверить XML по ней.
Полученная XLSX-книга даёт значения, но не все XML-теги и зависимости:
[шаблоны автозагрузки](https://www.avito.ru/autoload/documentation/templates)
и [проверка XML](https://autoload.avito.ru/format/xmlcheck/).
Condition для техники с пробегом — `Б/у`, а не видимое `Отличное` из
экспорта. Фото — JPEG/PNG, до 10; WebP сайта не передавать без подготовки.
Проверить title <=50 символов, description <=7500, характеристики и состояние;
успех текущего unit-теста фида не означает прохождение контрактных проверок.
Пилот — три подтверждённых смартфона с пробегом одной категории. Расширение возможно
после принятия фида и 72 часов без рассинхронизации.

## Описание После Замечания Поддержки

На 09.10.2026 поддержка связала отклонение т13 с фразой об уточнении наличия.
По команде владельца в шести текущих описаниях Avito она заменена на
«Напишите в чат, чтобы согласовать время просмотра». Новый генератор применяет
тот же вариант, включая обработку ранее одобренного текста. Изменённый текст
не наследует старое точное одобрение автоматически.

В `Price` остаётся реальная цена конкретного товара; товары без доступного
остатка исключаются действующими guards. Не дублировать цифру цены в Description
без механизма её синхронизации. Не менять ID и не создавать дубль отклонённого
объявления. Статус строки канала `active` означает включение в фид, не одобрение
модератором. После обновления дождаться отчёта очередной автозагрузки.

Подготовленная следующая партия — т9/т24/т26. Подтверждение их состояния не
разрешает запуск. Сначала одобрение описаний и QA накопительного XML на девять
ID; затем отдельный выкат с поддержкой девяти ID, backup и явной авторизацией.
Исторический шестистрочный оператор не использовать для этой новой партии.

[Выкат расширения Avito](avito-expansion-release.md).

На 07.10.2026 владелец подтвердил публикацию и QA первых трёх объявлений
т11/т29/т12, затем отдельно разрешил выкат т13/т14/т27 без ожидания 72 часов.
Production-фид по подключённой ссылке теперь содержит шесть объявлений;
отчёт загрузки и модерации новой тройки ещё ожидается. Генератор принимает 1–6 явных
стабильных ID, маршрут запрашивает максимум + 1 строку для обнаружения дублей.
Само увеличение лимита не добавляет товары: необходимы allowlist, активная
строка канала, подтверждённый mapping, готовый товар и проверенный остаток.

Следующая партия: т13/т14/т27. т20 — самостоятельный телефон с другим serial,
не дубль т13 по модели/памяти/цвету, но не входит в выбранную тройку. Батарея
т14 — 99% / 259 циклов; не переносить 100% / 0 из старого пилотного оператора.
Августовские даты диагностики сохраняются, новое измерение не заявляется.

Цвет Avito зависит от модели: у т14 / iPhone 16 Pro Max Desert Titanium
валидатор отклонил `бежевый`, владелец подтвердил `золотистый` в справочнике
модели. Сопоставление использует `avito_color(model, color)` для XML и XLSX;
название цвета в каталоге и описании не меняется. Общий dropdown цветов не
доказывает допустимость сочетания. Для других моделей Desert Titanium нет
автоматической догадки; требуется отдельная сверка. Владелец подтвердил успешную
проверку COLOR_FIXED XML для всех шести объявлений. Для будущих изменений
проверка целиком обязательна, даже если изменилось только одно поле.

Для отдельной проверки формата используйте `prepare_avito_expansion_review.py`.
Он принимает отчёт новой тройки из существующего pipeline, повторяет проверки
каталога/описаний/состояния/фото и добавляет её к точно захваченному живому XML.
Первые три `Ad`, включая ID, цены, описания и порядок фото, сохраняются целиком.
Входной SHA-256 и точный порядок трёх существующих ID обязательны. При изменении
живого фида нужен новый захват и ревизия; не обновлять hash вслепую.

```bash
python scripts/prepare_avito_expansion_review.py \
  --existing-feed /private/review/existing-live-feed.xml \
  --existing-sha256 <reviewed-sha256> \
  --existing-id <existing-id-1> --existing-id <existing-id-2> --existing-id <existing-id-3> \
  --pilot-review /private/review/pilot-review.json \
  --snapshot /private/review/catalog-snapshot.json \
  --public-preflight /private/review/public-preflight.json \
  --approved-copy /private/review/approved-copy.json \
  --output-dir /private/review/six-ad
npm run directus:avito:test
npm run directus:avito:test-expansion
```

Полученный XML — только файл для отдельного валидатора, НЕ для подключения
автозагрузки. Его manifest сохраняет неодобренные описания как pending и не
выдаёт подготовку за публикацию или подтверждение справочника Avito.
Проверка нового файла обязательна: прежний успешный отчёт относится к трём ID.
Не заменять подключённый источник файлом только новой тройки.

Порядок live rollout: отдельное одобрение текстов и проверка XML на шесть ID;
72 часа без рассинхронизации либо явно согласованное изменение этого правила;
свежая сверка остатка/цен/фото и первых трёх объявлений; отдельное разрешение
на выкат и публикацию, согласование дополнительных расходов при их наличии;
VPS backup; защищённое добавление трёх строк с сохранением старых, deploy и
расширение allowlist до ШЕСТИ. `activate_avito_pilot.py` — исторический оператор
первой тройки, для расширения не переигрывать. Сохранённая автозагрузка сама
подхватит изменение живого фида, поэтому это уже действие публикации.

### Текущее Состояние Пилота 2026-10-04

Актуальная подготовка — т11/т29/т12; т37 заменён только в локальном пилоте
из-за unmatched. Владелец подтвердил состояние/комплект/неизменность батареи
трёх устройств, затем уточнил: текущие устройства б/у, коробки открытые.
XLSX содержит Condition=Б/у и BoxSealed=Нет, RAM пилота — по аппаратным
источникам. Это не дефолт для будущих новых устройств.

Локальный XML-пример для QA опускает необязательный Set и зависимый BoxSealed;
комплект остаётся в Description. Это не опубликованный фид и не готовый файл
загрузки. Отдельный валидатор Avito уже подтвердил формат XML для всех трёх
пилотных Id (отчёт владельца 04.10.2026 23:32:59). Рассчитанное «Отличное»
не меняет входное Condition=Б/у. Валидатор не проверяет фотографии и модерацию.
Историческая связь и фактическое принятие аккаунтом не подтверждены, ID-link
API также возвращает 403. Перед активацией нужны кабинетная/схемная проверка,
сверка дублей и отдельное разрешение на выкат/публикацию. Все три пилотных
описания одобрены владельцем, включая отдельное одобрение точного текста т12;
это не разрешение на загрузку XML или публикацию.
Подробности и ограничения: [Пилот На Три Устройства](avito-pilot-review-2026-10-04.md).

Свежий предпусковой snapshot и HTTP-проверки подтвердили все три карточки,
сертификаты и 18 JPEG; XML побайтово неизменен. Владелец подтвердил отсутствие
действующей автозагрузки/других URL и несохранённую форму перехода. Старое
объявление остаётся неактивным и не будет активировано по решению владельца:
не включать его в пилот и не связывать автоматически с новым SKU. Определение
его SKU больше не требуется как условие именно этого пилота; будущая реактивация
потребует точной сверки. Подтверждения не разрешают выкат или публикацию.
Порядок кабинетной проверки без запуска и последующей активации:
[Проверка Перед Запуском Пилота](avito-pilot-activation-checklist.md).
