Обновлено: 2026-09-04. Статус: целевая схема. Первый этап (уведомления и принятие заявки) включён в production, проверена доставка из формы сайта; клиентский диалог ещё не реализован. Текущая реализация, проверки и сведения о выкате: `docs/telegram-leads-stage1.md`.

Пользователь подтвердил: первая версия должна включать общение с клиентами через бота. Остальные решения ниже — рекомендации. Базовое предположение: отвечает человек, бот маршрутизирует сообщения и отправляет служебные подтверждения.

ID группы `-1004317825276` определён по предоставленной владельцем ссылке `https://t.me/c/4317825276/2` и сохранён в локальном `TELEGRAM_CHAT_ID`. 2026-09-04 через API подтверждены bot ID `8694946838`, ожидаемая группа, включённые темы и административные права бота на управление темами и закрепление сообщений. ID группы уже заполнен. Далее запускать `node scripts/telegram_preflight.mjs` без `--discover-group`: поиск через ожидающие сообщения больше не нужен. Команда `/setup` не имеет обработчика и сама ID не возвращает.

2026-09-03 проверке мешала техническая ошибка автоматических разрешений Codex `404 Not Found`. 2026-09-04 сетевой запуск стал доступен; после ответа Telegram `401` пользователь обновил токен, и повторная проверка завершилась успешно (`ready: true`). Токен исключён из Git, запросы ограничены `api.telegram.org`, редиректы запрещены. Следующий шаг — изолированная проверка PostgreSQL и настоящих политик Directus; состояние подготовки описано в `docs/telegram-leads-stage1.md`.

Для токена подготовлен локальный файл `work/private/telegram.env`, исключённый из Git существующими правилами. Токен не передаётся через переписку. После его заполнения запускается:

```powershell
node scripts/telegram_preflight.mjs
```

Скрипт проверяет username, наличие webhook, ID группы, включённые темы и право бота управлять ими. Он не отправляет сообщения, не меняет webhook и не подтверждает ожидающие updates через offset. При действующем webhook обнаружение через `getUpdates` пропускается. Содержимое сообщений, токен и URL webhook не выводятся.

Если группа не обнаружена, владелец добавляет бота и отправляет в группу `/setup@isvoi_help_bot`, затем проверка повторяется. На этом этапе ответа на команду не будет. Числовой ID из результата сохраняется в локальной конфигурации; скрипт сам файл с токеном не перезаписывает. Успешная проверка подтверждает только готовность Telegram-ресурсов, не готовность всей интеграции.

## Первичная настройка владельцем

1. Открыть официальный [BotFather](https://t.me/BotFather) из аккаунта владельца и выполнить `/newbot`. Предлагаемое имя: `I СВОИ — помощь с техникой`. Варианты username: `isvoi_bot`, `isvoi_help_bot`; доступность проверяет BotFather, здесь она не проверена.
2. Сохранить выданный токен как пароль. Для обсуждения достаточно публичного `@username`; токен позже помещается в защищённое окружение сервиса, не в переписку или Git. Официальный [порядок создания бота](https://core.telegram.org/bots/tutorial#obtain-your-bot-token).
3. Создать закрытую группу `I СВОИ · Заявки · Белгород`, включить темы, добавить бота. Выдать боту управление темами; закрепление сообщений — только если включаем закреплённые карточки. Доступ сотрудников настраивается отдельно через привязки к Directus.
4. Подготовить отдельные тестовые бот и группу перед интеграционной проверкой. Не публиковать рабочую ссылку на сайте до подключения и проверки обработчика: одна регистрация в BotFather не запускает ответы.

Регистрация бота и создание группы сами по себе не подключают их к сайту. Разработку схемы и обработчиков можно выполнять до получения токена; он потребуется для проверки реального обмена сообщениями.

## Предлагаемый продукт

Один публичный бот I СВОИ для личных диалогов клиентов. Одна закрытая группа сотрудников с включёнными темами на первый магазин. На заявку создаётся отдельная тема; при расширении сети получатель определяется магазином.

Клиент видит переписку с ботом бренда и понятную подпись менеджера. Сотрудники видят карточку заявки, сообщения клиента и рабочие действия. Directus хранит заявки, переписку, назначения и результаты.

Пример карточки с вымышленными данными:

> Новая заявка · DEMO-001
>
> Покупка · iPhone 15 Pro 256 ГБ
>
> Магазин: Белгород
>
> Клиент подключил Telegram
>
> Статус: Новая · Ответственный: не назначен
>
> Взять в работу | Открыть в Directus

Телефон, email и полный текст анкеты не копируются в заголовки тем. Контакт доступен в карточке Directus; для переписки через бота телефон не требуется.

## Путь клиента

### После заявки на сайте

1. Форма сохраняет заявку обычным способом. Сбой Telegram не меняет результат сохранения.
2. Экран успеха показывает номер и дополнительную кнопку «Продолжить в Telegram».
3. Кнопка открывает бота с одноразовым параметром `start`. После запуска бот привязывает Telegram-аккаунт к уже созданной заявке и предлагает написать вопрос или отправить фото.
4. Менеджеру обновляется существующая тема. Второй лид не создаётся.
5. Если клиент не открыл бота, заявка остаётся в работе через оставленный контакт; карточка показывает «Telegram не подключён».

Бот не может первым начать личную переписку по телефону или `@username`: нужен запуск со стороны клиента. Это ограничение [Telegram](https://core.telegram.org/bots#how-do-bots-work). Передача параметра при запуске предусмотрена [deep linking](https://core.telegram.org/bots/features#deep-linking).

### Прямой вход в бота

Бот предлагает «Купить / подобрать», «Продать / обменять», «Другой вопрос». После выбора и первого содержательного сообщения создаётся лид. Сам `/start` не создаёт пустую заявку. Для расчёта Trade-in бот даёт переход на калькулятор сайта; суммы и правила не дублируются в боте.

При нескольких открытых обращениях клиент явно выбирает заявку. Новое сообщение не прикрепляется к произвольной последней записи. После закрытия бот предлагает продолжить прежний вопрос или создать новое обращение; успешная сделка не переводится автоматически обратно в работу.

## Работа менеджера

| Действие | Поведение |
| --- | --- |
| Взять в работу | Атомарно назначить сотрудника и установить `in_progress`; второй сотрудник увидит уже назначенного ответственного. |
| Ответить клиенту | Включить явный режим ответа для конкретных сотрудника, темы и заявки. Следующее сообщение становится черновиком с кнопками «Отправить клиенту» / «Отмена». |
| Отправить клиенту | Повторно проверить полномочия и получателя, записать исходящее сообщение и поставить его в очередь. Повторный клик не создаёт повторную отправку. |
| Заметка | Добавить внутреннюю запись в `lead_comments`; клиент её не получает. |
| Ждём ответа | Установить `waiting`; новое сообщение клиента возвращает активную заявку в `in_progress`. |
| Напомнить | Задать `next_action_at`; напоминание идёт сотруднику в рабочую группу. |
| Успешная / Закрыта | Запросить короткий результат, сохранить его в истории и обновить статус. |
| Открыть в Directus | Открыть обычную карточку, требующую входа в Studio. |

Обычный текст в группе остаётся внутренним. Нельзя пересылать клиенту всё содержимое темы или любую реплику в ответ на сообщение бота. Даже если Telegram даёт боту доступ к сообщениям группы, маршрутизацию определяет приложение.

Черновик ответа привязан к автору и имеет срок действия. Анонимные сообщения администраторов и публикации от имени канала не принимаются как действия сотрудника. Передача заявки другому менеджеру фиксируется отдельно; отвечать может назначенный сотрудник или руководитель.

Первый выпуск: текст и фотографии с подписями. Альбом обрабатывается как связанная группа вложений. Неподдерживаемый формат получает понятную просьбу отправить текст или фото. Голосовые, видео и произвольные документы — последующее расширение.

## Привязка и доступ

- Telegram ID сотрудника связывается с активным пользователем Directus и разрешённым магазином. Членство в группе само по себе не даёт права менять лиды.
- Telegram ID клиента и ID личного чата хранятся отдельно от изменяемого `username`. Совпадение имени, телефона или username не объединяет записи автоматически.
- Для привязки заявки: случайный непрогнозируемый токен, хранение только хеша, предлагаемый срок 15 минут, однократное погашение в транзакции. В ссылке нет контактов, UUID заявки или номера, который можно использовать вместо секрета.
- Токен выдаётся только в браузерной сессии, создавшей заявку. Текущий `idempotency_key` или `reference_code` не является доказательством доступа. Повторная выдача требует отдельного подтверждения владения сессией.
- Ссылка даёт право привязать текущий Telegram-аккаунт, но не раскрывает старую историю и контактные данные до проверки. Для уже связанного аккаунта повторное открытие безвредно; замена владельца автоматически запрещена.
- Webhook проверяет секрет, затем тип чата, ID отправителя и допустимость действия. Секреты находятся в окружении сервиса. Тестовые лиды и тестовые чаты изолированы от рабочих.
- Фото и история в Directus закрыты от Public. Обычные каталоговые права на файлы не должны распространяться на вложения клиентов.

## Техническая схема

Сайт → Directus `leads` → постоянная очередь → Telegram.

Telegram webhook → сохранённые входящие события → обработчик → переписка и действия в Directus → постоянная очередь → клиент или группа сотрудников.

Рекомендация: отдельный Node.js-процесс для Telegram и небольшое расширение Directus для защищённых операций. Общая база уже PostgreSQL; отдельная CRM или ещё один сервер для первой версии не нужны. Размер процесса и нагрузку проверять перед выкатом.

Операции «назначить», «изменить статус», «сохранить сообщение и задание доставки» должны быть транзакционными. Расширение проверяет полномочия реального сотрудника и фиксирует автора действия. Рабочий процесс получает отдельную ограниченную service identity, не admin token и не token публичного приёма лидов.

Предлагаемые сущности, точные имена и схема уточняются при реализации:

| Сущность | Назначение |
| --- | --- |
| `telegram_bindings` | Привязка клиента или сотрудника; связь сотрудника с Directus и областью доступа. |
| `lead_conversations` | Связь лида, клиента и темы рабочей группы, состояние диалога. |
| `lead_messages` | Направление, автор, текст, вложения, время, ID сообщений Telegram и результат отправки. |
| `telegram_link_tokens` | Хеш токена привязки, заявка, сессия, срок и факт использования. |
| `telegram_updates` | Постоянный входящий журнал с уникальным `(bot_id, update_id)` и состоянием обработки. |
| `telegram_outbox` | Задание доставки, ключ события, получатель, попытки, следующий запуск, ошибка и ID принятого сообщения. |

Новый лид и событие уведомления должны фиксироваться в одной транзакции. Предпочтительный вариант для событий `leads` — небольшой PostgreSQL-триггер, который пишет только идентификатор события в очередь. Он не вызывает Telegram по сети. Существующие триггеры и порядок миграций нужно проверить. Для диалогов сообщение и задание очереди создаёт транзакционный endpoint.

Простой Flow с единственным HTTP-вызовом недостаточен для переписки: дополнительно нужны постоянная очередь, обработка входящих сообщений, права и повторные попытки. Старый Python-скрипт можно оставить вспомогательным, но не делать вторым независимым механизмом рассылки.

## Сбои и синхронизация

- Webhook подтверждается после сохранения события. Обработка продолжается независимо от HTTP-запроса; повторная доставка события не создаёт новый лид, комментарий или исходящее задание.
- Рабочий процесс использует блокировку задания с истекающей арендой. После перезапуска незавершённые задания возвращаются в обработку.
- Изменения лида из Studio также обновляют карточку в Telegram; источником текущего статуса остаётся Directus. Собственные обновления карточки не создают цикл рассылки.
- Ограничение скорости и повтор после `429` учитывают `retry_after`. Для сетевого сбоя и `5xx` применяется задержка с увеличением интервала. Постоянная ошибка получателя становится видна оператору.
- Если Telegram принял сообщение, но HTTP-ответ потерян, результат неоднозначен. Повтор может создать дубль: абсолютную однократность доставки обещать нельзя. Для ответа клиенту такое состояние показывается как «результат неизвестен», автоматическая повторная отправка приостанавливается до решения оператора.
- «Принято Telegram» не означает «прочитано клиентом». Блокировка бота клиентом фиксируется как недоступный канал, а не успешный контакт.
- Для уведомления менеджеров предлагается целевая задержка до 10 секунд при доступных сервисах. Напоминания через 5 и 15 рабочих минут — обсуждаемые значения, не согласованный SLA.
- При первой активации задать границу запуска: старые лиды не рассылаются массово. Восстановление отдельных старых заявок — явное действие.

Контракты секретного webhook, callback-кнопок, тем, сообщений и ошибок сверяются с [Telegram Bot API](https://core.telegram.org/bots/api). Для создания тем в рабочей супергруппе боту требуется административное право управления темами. Лимиты отправки опубликованы в [Bots FAQ](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this).

## Дополнительная правка по результатам чтения кода

В `inferContactChannel` проверка email предшествует `startsWith("@")`, поэтому `@username` может распознаваться как email. При реализации переставить проверки и проверить обычный email, Telegram username и ссылку `t.me`. Это отдельная корректировка определения канала, не замена привязке Telegram ID.

## Порядок реализации и проверка

1. Уточнить рабочую группу, список сотрудников, часы ответа и содержание первого сообщения бота. Подготовить отдельного тестового бота и тестовую группу.
2. Реализовать схему, ограниченные права, очередь, webhook и наблюдаемость доставки. Проверить повторные события и восстановление после сбоя.
3. Реализовать темы, назначение и статусы. Проверить гонку двух менеджеров и обновление из Studio.
4. Добавить переход с сайта, прямой вход, клиентские сообщения и явную отправку ответа менеджером. Проверить сохранение исходного лида и невозможность привязки по одному номеру заявки.
5. Проверить текст, фото, несколько активных заявок, внутреннюю заметку, просроченный черновик, отозванный доступ, блокировку бота и неопределённый результат отправки.
6. Провести пилот с контролируемым клиентским аккаунтом. Включение в рабочую группу и production — отдельный выкат после проверки.

Критерий готовности: клиент с сайта продолжает ту же заявку в Telegram; уполномоченный менеджер отвечает из её темы; переписка и действия видны в Directus; внутренние сообщения не отправляются клиенту; сбои и повторы не теряют заявки и не скрывают ошибки доставки.

До production необходимо определить срок хранения переписки и фото, тексты уведомления о работе бота и порядок удаления истории. Эти продуктовые настройки должны быть согласованы с уже действующими документами сайта; в этом проекте сроки и юридические формулировки не устанавливаются.
