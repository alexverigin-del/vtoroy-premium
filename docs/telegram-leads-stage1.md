## Граница этапа

Новая заявка → очередь PostgreSQL → тема группы → карточка → «Взять в работу» → ответственный, статус `in_progress` и заметка в Directus. Изменение статуса/ответственного из Studio обновляет карточку.

Клиентский `/start`, привязка заявки с сайта, переписка, фотографии и напоминания остаются следующим этапом из `telegram-leads-design.md`. Не публиковать бота как работающий клиентский чат до готовности этого этапа. `/setup` не имеет обработчика.

Первый этап получает только нажатия кнопок через `getUpdates`. Webhook не создаётся и не удаляется. Если он уже задан, worker откажется запускаться. Перед переходом на webhook нужно остановить polling-worker и сохранить тот же журнал повторов.

## Реализация

- `scripts/setup_directus_telegram_sql.mjs` генерирует аддитивную миграцию. Новые маршруты, пользователи, разрешения и рассылка старых лидов автоматически не создаются.
- PostgreSQL-триггер в транзакции с новым лидом создаёт запись `telegram_deliveries`. Для текущих карточек изменение статуса/ответственного повышает версию.
- Расширение `directus-extension-isvoi-telegram` содержит четыре POST endpoint под `/isvoi-telegram`: `session`, `next`, `complete`, `update`. Без флага включения все закрыты. Public и admin-token не принимаются; требуется конкретная активная service identity с обычной ролью.
- Worker запускается отдельно от сайта. Он использует токен Telegram и ограниченный токен Directus, арендует единственный обработчик своего бота и отправляет только в группу из локальной конфигурации.
- Токен Telegram находится только у worker. В Directus передаются публичный bot ID и UUID service identity.
- Принятие заявки проверяет ID бота, группы, темы, сообщения, допуск сотрудника и магазин. Лид блокируется `FOR UPDATE`. Запись выполняется через `ItemsService` с accountability сотрудника, без admin bypass; заметка и назначение находятся в одной транзакции.
- При отказе в создании заметки savepoint откатывает и изменение лида. Отключённые сотрудники и неактивные пользователи не могут принимать заявки.
- Повторы callback и update не создают новых действий. Входящий курсор хранится в PostgreSQL и обновляется после обработки.

3. Создать активного service user с отдельной обычной ролью без прав на коллекции и без admin access. Статический токен поместить в env worker. UUID пользователя записать в `ISVOI_TELEGRAM_WORKER_USER_ID` на стороне Directus. Не использовать admin token или публичный токен приёма лидов.
4. Создать `telegram_routes`: магазин, тестовый bot ID, тестовый chat ID, `is_test=true`, `enabled=false`. Для заявок без `store_location_id` можно явно включить `accept_unscoped`; такой активный маршрут может быть только один на режим. До включения оставлять его выключенным.
5. Создать `telegram_staff`: route ID, числовой Telegram ID сотрудника, его активный пользователь Directus и `enabled=true`. Этот пользователь должен иметь обычные права на чтение/обновление лидов и создание `lead_comments` — например, соответствующие права `ISVOI Editor`. Один admin-only пользователь без обычных прав для этого пилота не подходит.
6. Заполнить env Directus: `ISVOI_TELEGRAM_BOT_ID`, `ISVOI_TELEGRAM_WORKER_USER_ID`, `ISVOI_TELEGRAM_MODE=test`, затем `ISVOI_TELEGRAM_ENABLED=true`. Собрать расширение и перезапустить Directus на стенде.
7. Создать отдельный env worker по `infra/telegram/.env.example`, указать тестовые реквизиты и ограниченный Directus token. Выполнить preflight с этим файлом. После проверки выставить `TELEGRAM_ENABLED=true`, `TELEGRAM_MODE=test` и включить тестовый маршрут. Не заменять уже сохранённый рабочий токен тестовым.
8. Запустить worker с явным файлом: `node scripts/run_telegram_worker.mjs --env <private-test-env>`. `--once` выполняет один рабочий цикл и может отправить сообщение: это не dry run.
9. Создать контролируемый тестовый лид (`is_test=true`) после включения маршрута. Дождаться темы и карточки, принять заявку, проверить автора, статус и заметку в Studio. Повторить двумя менеджерами, затем отключённым сотрудником. Отдельно проверить реальные row/field permissions и откат, когда создание комментария запрещено.

После пилота production включается отдельным выкатом с backup. Для него нужны production service identity, маршрут `is_test=false` и `TELEGRAM_MODE=production` на обеих сторонах. Смена bot ID/chat ID/магазина/режима существующего маршрута запрещена DB-триггером: она требует отдельной миграции, чтобы старые ID сообщений не отправлялись в новую группу.

Пример процесса PM2: `infra/telegram/ecosystem.config.cjs`. Шаблон использует `/opt/isvoi/infra/telegram/.env`. Этот файл исключается из Git. Нельзя включать несколько процессов одного бота; DB-аренда дополнительно защищает от случайного второго запуска. После аварии старой аренде может потребоваться до 90 секунд для освобождения.

## Работа с ошибками

| Состояние доставки | Действие |
| --- | --- |
| `pending` | Ожидает worker или отложенного повтора после ограничения скорости. |
| `in_flight` | Операция начата; результат ещё не записан. |
| `done` | Telegram принял актуальную карточку. Это не подтверждение чтения человеком. |
| `uncertain` | Результат создания темы/отправки неизвестен. Найти тему/сообщение в группе и сверить ID перед ручным восстановлением. Не сбрасывать вслепую в `pending`. |
| `failed` | Проверить `error_code`, права, блокировку бота или изменение маршрута. Исправить причину перед повтором. |

При `429` сохраняется задержка `retry_after`. При сетевой ошибке создание темы или сообщения не повторяется автоматически. Редактирование существующего сообщения допускает повтор; «message is not modified» считается успехом. Неопределённые редактирования ограничены восемью попытками. Сбой записи подтверждения в Directus повторяет только подтверждение, а не отправку в Telegram.

Карточка не содержит телефона, email, комментария клиента или UTM. Ссылка ведёт в обычную защищённую карточку Studio. Логи содержат только контролируемые коды ошибок; токены, URL webhook и тексты сообщений не выводятся.

## Отключение и границы восстановления

Остановить PM2-процесс, выключить `ISVOI_TELEGRAM_ENABLED` и нужный маршрут. Рабочие формы сайта сохраняют прежний HTTP-контракт. При остановленном worker и включённом маршруте новые задания накапливаются в PostgreSQL. При выключенном маршруте новые лиды в очередь не добавляются; их последующая отправка требует отдельного осознанного backfill.

Таблицы и история при отключении не удаляются. Сохранённые темы и сообщения остаются в Telegram. Клиентский диалог, смена магазина после создания заявки, переназначение через Telegram и удаление истории требуют следующих этапов; изменение магазина пока только убирает рабочие кнопки старой карточки, новую тему в другом магазине не создаёт.
