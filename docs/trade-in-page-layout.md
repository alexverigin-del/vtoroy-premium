# Trade-in: структура страницы и выпуск UX-обновления

Источник решения: [Figma / Trade page · UX structure](https://www.figma.com/design/cINpBQkJ5tuqHcD8jw3Ceo?node-id=30-175), страница `04 · Trade page · UX structure`. Реализация: 31.08.2026.

## Структура

1. `trade_hero` (10): короткое предложение, один основной CTA, каталог — ссылка.
2. `trade_calculator_intro` (15): постоянный H2, текст, пояснение о контактах, wizard.
3. `trade_paths` (20): продажа, консультация по комиссии, обмен.
4. `trade_steps` (30): заявка, диагностика, окончательная сумма, решение.
5. `trade_live_example` (40): актуальная товарная карточка и формула доплаты.
6. `trade_compare` (50): раскрываемое сравнение по трём критериям.
7. `final_cta` (60): помощь менеджера / ручная оценка. Повторный closing не выводится.

Порядок задаётся `page_sections.sort_order`, не зашит в JSX. Тексты заголовков и описаний берутся из Directus. Резервный контент находится в `apps/web/data/marketing-pages.json`.

## Поведение

- `TradeAnchor` переводит фокус к заголовку и прокручивает с учётом фиксированной шапки. Не перемонтирует wizard, не создаёт лишние history entries и не запрашивает новую оценку.
- При обычном входе нет принудительных focus/scroll. Шаги фокусируют H3 только после изменения; reduced motion отключает плавную прокрутку.
- Session restore выполняется после hydration. Телефон и комментарий не сохраняются. Состояние отправленной заявки не восстанавливается без номера и контактных данных.
- Модель сгруппирована по бренду из modelSlug серверной конфигурации. Группы готовятся серверным компонентом и передаются wizard как данные, без дополнительного клиентского кода группировки. Память зависит от выбранной модели; read-only поля категории и бренда удалены.
- Продажа и обмен ведут к `#trade-calculator`, при недоступных настройках — к `#final`.
- Комиссия ведёт в ручную форму с выбранной опцией комиссии. Сохраняется совместимый backend-контракт ручного обращения: `manual_evaluation`, намерение передаётся менеджеру в message. Расчёт комиссии не добавлялся.
- Старое `content.valuation.amount` больше не выводится. Редактируемая `content.valuation.formula` — объяснение, не quote. Персональные суммы остаются только в wizard.

## CMS-патчи и выпуск

Семь файлов `directus/content-patches/2026-08-31-*-ux.patch.json` применены к production 31.08.2026 в релизе `5bcbbea`. Они меняют только перечисленные поля `page_sections`, а не весь JSON. Согласия, юридические поля, pricing, товары, offers, фото и Passports не затронуты.

Код развёрнут, CMS-контент проверен на публичной странице. Сохранённые locks — история выполненного выпуска: не переснимать их ради повторного применения этих патчей. Для дальнейших изменений готовить новые патчи. CMS-контент имеет приоритет над fallback.

Процедура, выполненная для этого выпуска и обязательная для новых патчей:

1. Снять свежий lock существующей командой `npm run directus:content-patch -- --file <file> --capture-lock`.
2. Проверить field-level diff и выполнить preview/rehearsal без `--apply`. Selector по page + section_key обязан найти ровно одну строку; при несовпадении остановиться.
3. Зафиксировать проверенные патчи и код. Сохранить production backup по штатной процедуре.
4. После одобрения выката выполнить `--apply --confirm <patch-id>` штатным runner. Он проверяет lock, создаёт backup и инвалидирует site-content cache.
5. Задеплоить совместимый код и проверить порядок, заголовки и ссылки уже по production CMS.

Не менять `TRADE_WIZARD_ENABLED`: калькулятор уже включён отдельным предыдущим решением. Этот релиз не переутверждает цены и не публикует устройства.

## Проверки

- `npm run web:test:trade-layout`: порядок, группы моделей, CTA fallback, узкая область CMS-патчей и контракты focus/restore.
- `npm run web:verify` прошёл локально: audits, unit/контрольные расчёты, форматирование, lint, typecheck, Next 15.5.21 production build и bundle budget. Лимиты не повышались: общий JS 904,2 КБ raw / 289,3 КБ gzip / 249,8 КБ Brotli.
- `npm run web:smoke:trade-layout`: изолированный локальный Next + read-only mock Directus, desktop/mobile. API записи перехватываются локально; production credentials не используются.
- Итоговый smoke прошёл на desktop и mobile: вход без автоскролла, заголовки/порядок, якоря, модели, back/forward/reload, комиссия, ручная форма и локальный ответ об успешной отправке. Проверено отсутствие контакта/свободного текста в sessionStorage и безопасное восстановление после отправки; при неактивных настройках остаётся старая форма.
- Локальные screenshots: `output/playwright/trade-layout/`.
- На Windows Node 24.19 локальный smoke отключает native strip-types для Next (`NODE_OPTIONS=--no-experimental-strip-types`): иначе загрузчик Tailwind TS-конфига смешивает ESM и CommonJS. Это настройка тестового процесса, не production env.
- Перед production: `web:verify`, штатный Trade QA, визуальная проверка с настоящим CMS-контентом и текущими фото. Локальный fixture smoke не заменяет приёмку реальных заявок или проверку экранной клавиатуры на физическом телефоне.

Кодовые accessibility-метки и fallback формулы/раскрытия намеренно включены в content ownership baseline; редактируемые маркетинговые тексты остаются в CMS.
